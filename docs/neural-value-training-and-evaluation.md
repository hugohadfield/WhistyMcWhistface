# Whist learned-value MLP: training, validation, and playing-strength evaluation

This is a complete **supervised imitation of the Monte Carlo teacher**
pipeline with an explicit distinction between teacher imitation and
real playing strength. The network predicts an **eight-bin additional
tricks won distribution for every legal card**, from the *acting
player's own* `InformationState`. It cannot see real hidden hands.
The teacher continuation policy is part of the experimental definition.

## End-to-end workflow

From repository root, with optional PyTorch installed:

```bash
python -m pip install -r requirements-ml.txt

# 1. Generate whole, genuinely played games (all player observations).
python -m benchmarks.generate_training_games \
  --games 2000 --players 3 --seed 20262001 \
  --workers 16 --agents random,mc_random,mc_aware --rollouts 128 \
  --output-dir data/played-games

# 2. Label counterfactual cards using persistent state-parallel CPU MC.
python -m benchmarks.export_training_labels \
  --traces 'data/played-games/*.jsonl' \
  --output-dir data/whist-mc-1024 \
  --rollouts 1024 --workers 16 --policy bid_aware_2 \
  --seed 20262001 --state-batch-size 4 --shard-size 256

# 3. Train on GPU if available; otherwise CPU, with validation.
python -m benchmarks.train_value_model \
  --dataset data/whist-mc-1024 \
  --output-dir runs/whist-value-v1 \
  --device auto --batch-size 1024 --epochs 30 --patience 8 \
  --hidden-size 128 --residual-blocks 2 --lr 0.0003

# 4. Evaluate exactly once on unseen deal-group test examples.
python -m benchmarks.evaluate_value_model \
  --dataset data/whist-mc-1024 \
  --checkpoint runs/whist-value-v1/best.pt --split test \
  --output runs/whist-value-v1/test-metrics.json

# 5. Assess competitive score against frozen 1024-rollout MC.
python -m benchmarks.neural_vs_monte_carlo \
  --checkpoint runs/whist-value-v1/best.pt \
  --games 250 --rollouts 1024 --mc-policy bid_aware_2 \
  --workers 8 --device cpu --bootstrap 5000 \
  --csv runs/whist-value-v1/tournament.csv \
  --json runs/whist-value-v1/tournament-summary.json
```

**Important:** step 2 is typically the largest CPU cost. You do not
need a GPU to generate labels; PyTorch training is much smaller.
No full 2000-game dataset or 250-game tournament is generated by the
CI smoke test.

## Interrupting and resuming the expensive label export

Completed `.npz` shards are atomically committed as the exporter runs. If
interrupted before `manifest.json` exists, update to a version supporting
`--resume` and **repeat the exact same labeling command with `--resume`**:

```bash
python -m benchmarks.export_training_labels \
  --traces 'data/played-games/*.jsonl' \
  --output-dir data/whist-mc-1024 \
  --rollouts 1024 --workers 4 --policy bid_aware_2 \
  --seed 20262001 --state-batch-size 4 --shard-size 256 --resume
```

Use the same input trace files/order, seed, rollout count, and shard size.
The resume logic verifies saved decision seeds and rollout counts, then skips
the already-flushed prefix *independently for train, val and test*. This is
important because each split has its own incomplete in-memory buffer.
Unflushed work is recomputed, but completed shards are neither overwritten
nor relabeled. A finalized dataset with `manifest.json` needs no resume.

For faster *remaining* labels, explicitly opt into a mixed sampling budget:

```bash
# Example: resume existing 1024-rollout shards, use 256 for new decisions.
python -m benchmarks.export_training_labels \
  --traces 'data/played-games/*.jsonl' \
  --output-dir data/whist-mc-1024 \
  --rollouts 256 --workers 4 --policy bid_aware_2 \
  --seed 20262001 --state-batch-size 4 --shard-size 256 \
  --resume --allow-mixed-rollouts
```

Existing completed shards retain their original 1024 sampled futures,
new shards record 256 per action. The manifest reports `"mixed"` and lists
the distinct budgets; per-row `n_rollouts` controls target normalization.
This reduces the rollout work **per remaining state** by a factor of four,
but the new distributional labels have roughly twice the Monte Carlo
standard error. Run a held-out evaluation before treating mixed-budget
training as equivalent to 1024-future labels. Without the explicit
`--allow-mixed-rollouts` flag, a changed budget is rejected.

This option cannot change the performance of a Python process that is
already running; a source-code change only affects processes started after
you update the repository.

## Profile neural-guided search before scaling rollouts

The main tournament runs separate game worker processes, so simply
invoking `python -m cProfile -m benchmarks.neural_rollout_tournament
--workers 4 ...` profiles mostly the **parent process**. Instead use
the dedicated single-process, real-game profiler:

```bash
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
python -m benchmarks.profile_neural_rollout \
  --checkpoint runs/large-190k-v1/best.pt \
  --rollouts 32 --rounds 3 --seed 90061101 \
  --output-prefix runs/large-190k-v1/profile-neural-mc-32
```

The profiler runs the first three rounds (7, 6 and 5 cards), with
neural-guided MC in seat 0, the **same frozen model without MC** in seat
1, and a random player in seat 2. It uses the tournament's deterministic
deal seeds. **Only nonforced neural-guided move selection is profiled:**
bidding, trump selection, and the opponents' ordinary moves are excluded.

Outputs:

- `profile-neural-mc-32.prof`: full standard `cProfile` binary;
  inspect interactively with `python -m pstats <path>`, or SnakeViz.
- `profile-neural-mc-32.txt`: top 75 functions by cumulative time and
  top 75 by self time.
- `profile-neural-mc-32.json`: aggregate timings for
  `InformationState.apply_public_event`, observation validation,
  `encode_decision`, neural inference, hidden-hand sampling, card
  simulation and related stages.

For a full 13-round profile, set `--rounds 13`. For a quick repeated
A/B experiment, keep `--rollouts`, `--rounds`, and `--seed` fixed,
and profile before/after the code change.

**Interpretation:** Cumulative times include callees and therefore
overlap; don't add them together. `cProfile` itself slows Python calls,
especially frequent small methods, so use the normal **unprofiled**
tournament to measure real end-to-end throughput. Use this diagnostic
profile primarily to identify the highest-impact optimization.

## Evaluate the neural-guided Monte Carlo bot before labeling more data

`NeuralRolloutMonteCarloPlayer` is an actual playable bot: it performs
Monte Carlo action selection, assumes the *frozen 190k neural net*
controls its future simulated moves and `bid_aware_2` controls sampled
opponents. It inherits the same bidding/trump selector as the direct
neural and ordinary MC players. Its model never sees sampled private
opponent hands.

Compare it directly to the pure neural bot using full matched-deal,
seat-swapped games:

```bash
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
python -m benchmarks.neural_rollout_tournament \
  --checkpoint runs/large-190k-v1/best.pt \
  --baseline neural --games 20 --rollouts 32 \
  --workers 4 --seed 90061101 \
  --json runs/large-190k-v1/neural-mc-vs-neural.json
```

This is an initial *speed and correctness* tournament. It prints interim
progress and final paired-bootstrap 95% intervals. Don't interpret just
ten deal pairs as a reliable playing-strength estimate. Increase to
100+ matched games, preserving new independent seeds, only if the
32-rollout experiment is computationally practical.

For an MC baseline rather than pure neural, specify `--baseline mc`
and `--baseline-rollouts 128`. The `--rollouts` flag sets the
**neural-guided searcher's** budget, not the baseline budget.
Each candidate card uses the same hidden samples as other candidates,
and all rollout policies are observer-safe.

**Search budget and CPU time matter.** Even with batched neural forward
passes, simulated observation updates are expensive, so do not
start with 1024 neural-guided rollouts. Measure runtime and strength
separately; a search policy that matches the net but costs much more
does not yet justify replacing it.

## Neural self-continuation: first policy-iteration experiment

After training a strong frozen model, use it **only for the original
observer's future decisions** in the counterfactual rollouts. Opponent
moves remain `bid_aware_2`, so changing teacher targets tests a single
hypothesis: the original MC teacher underestimated actions requiring
intelligent future self-play.

```bash
# First run a small, independent experiment: source trajectories may be
# random, but choose new game seeds for later meaningful evaluation.
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
python -m benchmarks.export_training_labels \
  --traces 'data/large-traces/*.jsonl' \
  --output-dir data/neural-self-smoke \
  --max-states 64 --rollouts 128 --workers 4 \
  --policy self_neural --self-checkpoint runs/large-190k-v1/best.pt \
  --seed 80116102
```

At each simulated card, the complete sampled hands are used **only by the
fast game simulator** to enforce legal moves and outcomes. The observer's
information snapshot is advanced separately with public `card` and
`trick_end` events, and its own remaining hand. **The neural network
never sees a simulated opponent's private cards.** A forced self move
requires no network call; nonforced self decisions are batched over a
group of simulated futures. The model is cached per labeling worker.

The resulting labels are tagged `teacher_policy=self_neural`, with
the checkpoint SHA-256 and `bid_aware_2` opponent continuation stored
in `manifest.json` and `teacher-policy.json`. Resuming a stopped
export verifies this provenance, so different frozen models cannot be
silently mixed. This is a new teacher-policy dataset: don't compare its
raw supervised losses to `bid_aware_2` test losses as though they
measured the same target.

**Cost caution:** Even with batched neural calls, reconstructing the
observer's knowledge and encoding it adds significant cost compared to
fast integer-only `bid_aware_2` rollouts. Benchmark the 64-state
smoke run before scaling up to thousands of examples. A full 190k-state
neural-continuation re-label is not a sensible first experiment.

For a clean next iteration, generate new game trajectories with new seeds,
keep whole-game train/val/test splits disjoint from original held-out
evaluation, train on the new neural-self targets, and compare complete
gameplay against the frozen 190k policy and Monte Carlo. **Policy iteration
is not guaranteed to improve** in an imperfect-information game with
approximate values.

## Training

`benchmarks.train_value_model` reads one compressed `.npz` shard at a
time, shuffles training shard order and rows reproducibly each epoch and
uses AdamW, gradient clipping, and distributional soft-label cross entropy.
It checks the feature and label schemas and enforces nonempty **whole-deal
train, validation and test splits**. It never uses test data for model
selection.

Use `--device auto` to choose CUDA, Apple Metal MPS or CPU in that
order; force `--device cpu` for CI. Defaults: 128 hidden units, two
residual blocks (316,448 parameters), batch size 512, 30 epochs,
learning rate 3e-4 and patience 8.

Outputs:
- `best.pt`: lowest **validation action cross entropy** checkpoint,
  ready to use with NeuralValuePlayer.
- `last.pt`: final epoch checkpoint for diagnosis.
- `history.csv`: per-epoch training CE, validation CE/MAE/RMSE, card
  choice agreement, and expected-score regret.
- `training-config.json` and `result.json`: exact hyperparameters,
  teacher provenance, parameter count, and checkpoint selection.

Checkpoints use `torch.load(..., weights_only=True)` and validate
checkpoint version, feature schema, dimensionality and architecture.
Changing feature representation requires a new checkpoint schema.

## Held-out metrics: what they do and don't say

`benchmarks.evaluate_value_model` calculates:

| Metric | Interpretation |
|---|---|
| Action cross entropy | Per-legal-card soft-label classification error |
| Action Brier | Sum of eight squared probability-bin errors per legal card |
| Expected round-score MAE/RMSE | Predicted vs MC teacher expected score in points |
| Teacher top-1 card agreement | Exact argmax agreement including deterministic ties |
| Teacher-optimal agreement | Allows ties within 1e-6 MC point |
| Teacher expected regret/decision | Teacher's highest Q minus teacher Q of model's chosen card |

The label counts are *sampled estimates*, not perfect-play ground truth.
These are **teacher-relative** metrics. The test script evaluates the
dataset's `test` split by default and refuses teacher-policy mismatches.
Use a separate higher-rollout **test-only** dataset if you want more
precise reference labels (same feature schema and teacher semantics).

A small held-out test split is not meaningful: generate sufficient
independent deal groups and keep all seat-swapped games together. Never
train on the test split or tune decisions using the tournament results
without reserving a fresh independent benchmark.

## Actual game play and paired tournaments

`NeuralValuePlayer` is a standard `Player` subclass, requiring a
trained `checkpoint`. It inherits **the exact same trump selection and
bidding algorithms** as `MonteCarloPlayer` and replaces *only card
selection*. It loads its network lazily, caches it in memory and always
plays legal cards. It uses only `game.observe(player_id)` for features.
For forced actions it doesn't need model inference.

The paired 3-player tournament runs **two full 13-round matches per
deal seed**, swapping the seats occupied by the neural and MC players.
The third seat is occupied by an unchanged random player. Each round's
deal uses a fixed seed independent of prior policy RNG consumption, so
both variants get matched initial hands in each pair.

Reported mean score difference and bootstrap confidence intervals are
computed over **deal pairs**; the per-game raw CSV is also kept.
This is a three-player benchmark, not evidence of strength for all 2–7
player formats. You can vary `--mc-policy` and `--rollouts`, but always
record them, since they fundamentally change the baseline.

A model that imitates an MC teacher with weak random continuations may
still play poorly against stronger opponents. Competitive evaluation,
preferably against multiple opponent styles, is indispensable.

## GitHub Actions / local workstation

The opt-in `neural_training_end_to_end` PR job:
1. Installs **CPU-only PyTorch** and runs real-data integration tests.
2. Creates eight independently seeded full games.
3. Labels all non-forced decision states at a cheap 16-rollout budget,
   with split groups containing train, validation and test.
4. Trains the small MLP for three CPU epochs.
5. Evaluates the untouched test split.
6. Plays a **two-game paired** neural vs MC head-to-head.
7. Archives checkpoint, histories, metrics, raw traces, shards and scores.

This is a **pipeline test**, not a claim that the tiny model is strong.
GitHub Actions artifact retention is 14 days; copy anything useful to
durable storage. For a serious dataset and training run, use a local CPU
server for parallel labels and a GPU for faster experimentation on the
model, but the MLP does not *require* a GPU.

Suggested research stages: calibrate on 100–500k positions; measure
held-out Q regret; then run matched 1024-rollout tournaments. Only scale
toward millions of examples if those metrics warrant it.
